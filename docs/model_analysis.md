# Заметки По Анализу Модели

## Постановка задачи

В этом репозитории задача оттока клиентов рассматривается как бинарная классификация:

- `Yes` означает, что клиент с высокой вероятностью уйдёт.
- `No` означает, что клиент с высокой вероятностью останется.

Для junior ML portfolio это хороший выбор, потому что здесь сочетаются классический tabular ML и практический сервисный слой.

## Стратегия split-ов

В обучающем пайплайне используются три выборки:

- Train для обучения кандидатных моделей.
- Validation для выбора модели и настройки threshold.
- Test для финальной честной оценки.

Это сильнее, чем выбирать модель сразу по test, потому что так мы не протекаем решениями по валидации в финальный benchmark.

## Логика выбора модели

Обучаются две кандидатные модели:

1. Logistic Regression
2. HistGradientBoostingClassifier

Продакшен-кандидат выбирается по validation `roc_auc`.

Почему именно `roc_auc`:

- Churn сначала является ranking-задачей, а уже потом задачей классификации.
- `roc_auc` показывает, умеет ли модель ставить более рискованных клиентов выше менее рискованных.
- Эта метрика не зависит от threshold, поэтому хорошо подходит для отбора модели.

## Логика настройки threshold

После выбора модели classification threshold настраивается на validation split по `f1`.

Почему threshold настраивается отдельно от выбора модели:

- Выбор модели отвечает на вопрос: какая модель лучше ранжирует клиентов по риску?
- Настройка threshold отвечает на вопрос: где бизнесу проводить границу между положительным и отрицательным классом?

В текущем запуске для выбранной logistic regression использован threshold `0.6096`, а не дефолтный `0.5`.

## Что говорят текущие метрики

Выбранная модель на последнем запуске:

- Модель: `baseline_logistic_regression`
- Validation ROC-AUC: `0.8362`
- Test ROC-AUC: `0.8415`
- Test recall: `0.7005`
- Test F1: `0.6136`

Сводка cross-validation для выбранной модели на development data:

- ROC-AUC: `0.8464 +/- 0.0072`
- Recall: `0.8020 +/- 0.0134`
- F1: `0.6310 +/- 0.0126`

Интерпретация:

- Модель ведёт себя достаточно стабильно между фолдами.
- Recall выше precision, что часто разумно для churn-сценариев, где пропустить рискованного клиента бывает дорого.
- Boosting-модель конкурентная, но baseline logistic regression всё равно выиграла по validation ROC-AUC.

## Бизнес-интерпретация важных признаков

Топ признаков по permutation importance:

1. `tenure`
2. `InternetService`
3. `Contract`
4. `MonthlyCharges`
5. `TotalCharges`

Разумная бизнес-интерпретация:

- Клиенты с небольшим сроком обслуживания чаще склонны к оттоку.
- Тип контракта важен, потому что клиентов с month-to-month проще потерять.
- Monthly charges и total charges отражают чувствительность к цене и стадию жизненного цикла клиента.

## Текущие ограничения

- Пока нет hyperparameter tuning сверх вручную выбранных настроек.
- Нет анализа calibration.
- Нет fairness-проверок по пользовательским подгруппам.
- Нет experiment tracker вроде MLflow.
- Нет production monitoring и drift checks.

Это хорошие направления для следующего этапа, но для первого сильного portfolio-проекта их отсутствие нормально.

## Что говорить на собеседовании

- Я не выбирал финальную модель по test set.
- Я разделил ranking quality и решение о classification threshold.
- Я довёл проект до API, а не остановился на notebook-метриках.
- Я добавил тесты на артефакты обучения, корректный inference и failure-сценарии API.
